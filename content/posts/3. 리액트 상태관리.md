## 1. React 상태관리

### 상태 관리란?

상태 관리는 React에서 화면에 따라 변경되는 데이터를 저장하고, 변경하고, 필요한 컴포넌트에서 사용할 수 있도록 관리하는 것임.

간단한 상태라면 `useState`만으로 충분함.

그러나 챙김의 대화형 상황 입력을 예로 들면 다음과 같이 여러 상태가 생길 수 있음.

- 현재 이벤트 = 이사
- 현재 질문 = 3
- 지역 = 경산
- 예정일 = 10월 20일
- 주거 형태 = 월세
- 첫 독립 여부 = `true`

그리고 이러한 정보가 질문 화면뿐만 아니라 다른 컴포넌트에서도 필요할 수 있음.

따라서 규모가 커지면 `useState`만으로 모든 공유 상태를 관리하는 것보다 **전역 상태 관리 방법**을 사용하는 것을 고려해야 함.

### 지역 상태와 전역 상태

**지역 상태(Local State)** 는 특정 컴포넌트 안에서만 사용하는 상태임.

**전역 상태(Global State)** 는 여러 컴포넌트에서 함께 사용하는 상태임.

### Props를 이용한 상태 전달

React에서는 부모가 가진 State를 Props로 자식에게 전달할 수 있음.

```jsx
function Parent() {
  const [name, setName] = useState("길동");

  return <Child name={name} />;
}
```

자식 컴포넌트에서는 전달받은 값을 다음과 같이 사용할 수 있음.

```jsx
function Child({ name }) {
  return <p>{name}</p>;
}
```

작은 구조에서는 이러한 방법만으로도 충분함.

### Props Drilling

Props Drilling은 부모가 가진 데이터를 아래쪽 자식에게 전달하기 위해 **Props를 여러 컴포넌트를 거쳐 계속 전달하는 현상**임.

### 전역 상태 관리가 필요한 이유

컴포넌트가 많아지면 중간 컴포넌트까지 계속 Props를 전달해야 하는 상황이 발생할 수 있음.

**Props로 데이터 전달 → 컴포넌트 증가 → Props Drilling 발생 → 상태 공유 복잡도 증가 → 전역 상태관리 고려**

Zustand 같은 전역 상태관리 라이브러리를 사용하면 필요한 컴포넌트가 상태를 직접 가져올 수 있어 Props Drilling을 줄일 수 있음.

## 2. 상태관리 방법 비교

### Context API

Context API는 React에서 기본으로 제공하는 기능으로, 여러 컴포넌트가 데이터를 공유할 수 있게 해줌.

Props를 사용하면 일반적으로 다음과 같이 데이터를 전달함.

**Parent → Child → Child → Child**

Context API를 사용하면 중간 컴포넌트에 Props를 계속 전달하지 않고 필요한 컴포넌트에서 데이터를 가져와 사용할 수 있음.

쉽게 말하면 **여러 컴포넌트가 같이 사용할 데이터를 한 곳에서 공유할 수 있도록 해주는 React 기능**임.

**장점**

- React에서 기본으로 제공하기 때문에 별도의 라이브러리를 설치하지 않아도 됨
- Props Drilling을 줄일 수 있음
- 간단한 전역 상태를 공유하기 좋음

**단점**

- 관리해야 할 상태가 많아지면 코드가 복잡해질 수 있음
- 상태를 변경하는 기능까지 많아지면 관리하기 불편해질 수 있음
- 규모가 커지면 상태 관리를 위한 별도의 라이브러리가 더 편할 수 있음

### Zustand

Zustand는 React에서 사용할 수 있는 전역 상태관리 라이브러리임.

여러 컴포넌트에서 같이 사용해야 하는 상태를 **Store**에 저장하고 필요한 컴포넌트에서 가져와 사용할 수 있음.

Store는 여러 컴포넌트가 같이 사용할 상태를 보관하는 공간이라고 생각하면 됨.

**Zustand 설치 → Store 생성 → Store에 상태 저장 → 필요한 컴포넌트에서 상태 사용 → 상태 변경 시 화면 반영**

**장점**

- 코드가 비교적 간단함
- Props를 여러 단계로 전달하지 않아도 됨
- 필요한 컴포넌트에서 Store의 상태를 가져와 사용할 수 있음
- 여러 개의 공유 상태를 관리하기 편함

**단점**

- React 기본 기능이 아니기 때문에 별도로 설치해야 함
- 모든 상태를 무조건 Store에 넣으면 오히려 상태 관리가 복잡해질 수 있음
- 특정 컴포넌트에서만 사용하는 간단한 상태는 `useState`가 더 적절함

### Recoil

Recoil도 Zustand와 마찬가지로 React에서 사용할 수 있는 전역 상태관리 라이브러리임.

Recoil에서는 상태를 **Atom**이라는 단위로 만들어 관리함.

Atom은 하나의 상태를 저장하는 작은 상태 저장 공간이라고 생각하면 됨.

예를 들면:

- 이벤트 Atom → `"이사"`
- 지역 Atom → `"경산"`
- 날짜 Atom → `"10월 20일"`

필요한 컴포넌트에서 특정 Atom을 가져와 사용함.

**장점**

- 상태를 작은 단위로 나누어 관리할 수 있음
- 필요한 Atom만 컴포넌트에서 사용할 수 있음
- Props Drilling을 줄일 수 있음

**단점**

- 별도의 라이브러리를 설치해야 함
- Atom이라는 개념을 추가로 이해해야 함
- 챙김에서 필요한 상태 관리 수준에서는 Zustand처럼 더 간단한 방식으로도 충분히 구현할 수 있음

### 상태관리 방법 비교

| 구분 | Context API | Zustand | Recoil |
| --- | --- | --- | --- |
| 종류 | React 기본 기능 | 상태관리 라이브러리 | 상태관리 라이브러리 |
| 별도 설치 | 필요 없음 | 필요함 | 필요함 |
| 상태 관리 방식 | Context를 통해 데이터 공유 | Store에 상태 저장 | Atom 단위로 상태 저장 |
| Props Drilling 해결 | 가능 | 가능 | 가능 |
| 사용 난이도 | 간단한 상태에서는 쉬움 | 비교적 간단함 | Atom 개념을 알아야 함 |
| 여러 상태 관리 | 상태가 많아지면 복잡해질 수 있음 | 편리함 | 상태를 나눠서 관리 |

## 현재 진행 중인 캡스톤 챙김에서는 어떤 방식을 사용할 것인지

챙김에서는 **Zustand를 사용하는 것이 적합하다고 판단함.**

챙김의 대화형 상황 입력에서는 다음과 같은 여러 상태가 생길 수 있음.

- 현재 이벤트
- 현재 질문 단계
- 사용자가 입력한 답변
- 선택한 지역
- 날짜
- 주거 형태

이러한 상태 중 여러 컴포넌트에서 같이 사용해야 하는 상태를 Zustand Store에서 관리할 수 있음.

Context API도 사용할 수 있지만 공유해야 하는 상태와 상태 변경 기능이 많아질 경우 관리가 복잡해질 수 있음.

Recoil도 사용할 수 있지만 챙김에서 필요한 상태 관리는 Zustand의 Store 방식으로 충분히 구현할 수 있고 구조도 비교적 간단함.

따라서 다음과 같이 구분하여 사용하는 방향이 적합함.

**한 컴포넌트에서만 사용하는 간단한 상태 → `useState`**

**여러 컴포넌트에서 공유해야 하는 상태 → `Zustand`**
